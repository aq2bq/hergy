# hergy

`hergy` boots a team of AI agents onto herdr from YAML team definitions. It sits one level above herdr: it boots the team from your team definition and hands each member its first prompt, while herdr runs the panes and carries the messages.

The shape of every command and flag lives in `hergy cheat --ai`. Read that before you type one; this file holds only the judgement. `hergy <command> --help` prints one command's page: its flags, each with what it means for that command.

## Choose between hergy and herdr

- Starting a team, adding a worker, closing a team: hergy.
- Reaching a teammate, driving a pane: herdr.
- Whether anyone is waiting on the human, or nobody is working: `hergy status`. A member whose screen has not changed while it works is marked with how long it has stood.

## Team definitions and team names

- A team definition is the directory `teams/<name>/` with its `team.yaml`; `hergy up`, `hergy new` and `hergy show` take a team definition name.
- `team.yaml` must write `mission:` — one line saying what the team is for. A definition that writes none, or writes one over more than one line, does not read. The commands that handle a team print it at the top of their header, and so do the web UI's team list and team screen.
- A team is a running team, named by `hergy up --as` or, without it, by the team definition name; `hergy down`, `hergy status`, `hergy apply`, `hergy refresh`, `hergy reprompt`, `hergy hire`, `hergy focus`, `hergy nudge`, `hergy stop` and `hergy tell` take a team name and find the definition from this machine's launch record. The team's herdr tab is labelled with the team's name alone, so a tab a person sees says the team, not the definition it came from; a team booted by an older hergy still has the definition in its tab's label, and is still found.
- `hergy status` with no team name lists every running team, with its team definition name.

## Before you run one

- Prove the plan with `--dry` before `hergy up`, `hergy down`, `hergy apply`, `hergy refresh` or `hergy hire`. `up --dry` reads no herdr (it names a team definition). `reprompt --dry`, `hire --dry`, `nudge --dry`, `stop --dry` and `tell --dry` also read no herdr, so a team that is not running can be planned for: name it with `--team` (a team name, or a team definition name the launch record does not know), and with no `--team` the one team in this project's launch record is used. `down --dry`, `apply --dry` and `refresh --dry` read the live agents and tabs.
- `hergy apply` is the one operation that puts a changed definition into a running team: hergy compares the saved definition with the prompt each member last read and decides the way for each member — send the prompt again (`resend`, the conversation stays), start it (`start`, the definition has it and no agent is live), restart it (`restart`, its kind or args changed, so the conversation goes), or say it cannot (`cannot`, with the reason). A member that is working or waiting for permission is left, with the reason, and the rest go on; the command answers 1 while one is left. Name the members, or apply every member with drift. After editing a document or a prompt, apply sends the prompt again with a preamble saying what changed; after editing a profile, apply restarts the member.
- `hergy reprompt` and `hergy refresh` stay as the single-purpose tools: `reprompt` sends the bootstrap prompt again (with the preamble when the definition changed), and `refresh` restarts a member, for one that is stuck. `refresh` ends the agent and starts it again, so the conversation starts empty; a member that is no longer running is started again in the pane hergy named after it, when that pane is still at its shell; if the pane is busy, it changes nothing and points at `hergy down` then `hergy up`.
- To add a member to a running team, write it in `team.yaml` and run `hergy apply <member>`: hergy makes it a pane in the team's tab and starts it there, the way `hergy up` starts a member, so it reads the same rules and is handed the same bootstrap prompt. `hergy refresh <member>` refuses a member with no pane and names `hergy apply`. A team that is not running (no tab of its own) is refused, and `hergy up` is named.
- A member cannot `refresh` itself: hergy runs inside a member's pane, and stopping that member would stop hergy before it could start the agent again. Run it from another pane, or as the human.
- `env` is fixed when a pane is made: after changing `env`, run `hergy down` then `hergy up`; apply says so and does not restart the member, and `hergy refresh` keeps the pane and its env.
- `hergy` sets `GY_ACTOR=<herdr name>` in every pane it makes, so an agent's records in gy carry the name herdr knows it by; the bootstrap prompt tells the agent not to change it. A profile that writes `GY_ACTOR` does not win, and `hergy validate` warns when one does.
- `hergy down` closes the panes of the team you are in, your own pane included, and that pane last. A pane is closed whether an agent stands in it or not (a member that never started, or whose agent ended, goes too), and a pane hergy did not name is a person's own and stays. A team whose boot stopped before any agent ran is still put away by `hergy down <team>`.
- To read output, add `--lang en`, or use `--dry --json`; the `next:` line names what to type next. `--lang` is the command line's language: the WebUI that serve opens is Japanese whatever `--lang` says.
- `hergy up`, `hergy hire`, `hergy apply` and `hergy refresh` may wait: a new agent can ask a question while it starts (whether to trust this folder, for example). Run them in the background and read their output. The wait begins with a line naming the member, the tab and the pane; tell the person which pane to answer in, and wait for them. Do not answer that question yourself (no `send-keys`), do not write the agent's trust settings, and do not move their focus. If the person stops with Ctrl-C, the last line says how to go on.

## Reaching a member

- `hergy focus <member>` moves herdr's focus to that member's pane, so a person can answer it there.
- `hergy nudge <member> [text]` sends a short push to carry on, only when the member is idle or done: a working or blocked member is refused, and nothing is sent. With no text it sends a short "carry on". The text is headed by who sent it: the member whose pane you type in, else the human.
- `hergy stop <member>` sends esc, ending the member's current turn and keeping its conversation; a member that is not working is left alone, and the command still succeeds. Some agents need esc twice, the first only asking them to interrupt: hergy watches the member's state after each esc and sends a second only while the member is still working, so an agent that stopped on the first is never sent a second. A member still working after two escs is reported as not stopped (exit 1), and `hergy refresh <member>` is named as the next step — the same step a stop that worked names. A member cannot stop itself: hergy runs in that member's pane.
- `hergy tell <member> "<text>" [--from <member>]` sends a message headed by `--from`, else the member whose pane you type in, else the human. It does not read the member's state, so the message reaches an agent in any state. A `--from` name outside the team is refused.
- All four take a member by short member name or herdr name, and `--team <team>` picks the team; none needs a herdr-managed pane of its own. `--dry` prints what would be sent, reads no herdr and sends nothing (focus has no `--dry`).

## While you are inside a team

- The lead adds workers within its `workers:` (from, purpose and profile) and gives each a short name. `hergy hire --purpose` must be a purpose the hiring member's `workers:` names, and the profile comes from that entry (a hire does not choose one); a purpose outside it is refused, naming the purposes the member may hire for. With no `--from`, it uses the one member that hires for that purpose (two or more stop the hire and are listed).
- `turns:` says who hands the turn to whom (a member's name, or `human`). Each member and the human hand the turn on to at least one party, and at least one turn reaches the human; a definition that does not say so stops hergy the way a file that does not read does, so `up`, `refresh`, `reprompt`, `hire` and `validate` all stop with the same sentences. A rule text that still writes "a → b" is compared with `turns:` and warned about when they disagree.
- `ledger:` says which member may make which write to gy: each entry is `<write> by <member>[, <member>...]`, where `<write>` is the name of a gy write (`req approve`, `decide`, and the like) or `question to human` for a question whose decider is nobody in the team, and `<member>` is a `members[].name` (a worker's name cannot be written). It stops nothing: `hergy validate` warns once for each write a writer of the team (`GY_ACTOR` begins with the team name, or the name the launch record shows) made that the rule gives to other members, and says so in one line when gy cannot be read.
- A worker reports back to the member that hired it when the work is done.

## While you write settings from outside

- Write with `hergy new` (it writes into the project's `.hergy/` inside a git repository, and into `~/.config/hergy/` outside one), edit, `hergy validate`, then show `hergy up --dry` to the person before `hergy up`.
- A role's name is an identifier: `roles/<role>.yaml` is read by the role name, which matches `[a-z][a-z0-9_-]{0,31}`; the name people read goes in the document's title. A role document whose file name is not one is broken: `hergy validate` says so (naming the document, the name and how to fix it — rename it on the roles screen and the save changes the team definitions that read it), and `up` of a team that reads it stops with the same sentence.
- `hergy validate` prints the size of each team definition (the part of its rules that goes into the prompt, plus the words of its templates) and of each role document (the part that goes into the prompt), and warns over the provisional budget (3,000 characters each). It checks a role document once, not once per team that uses it. A warning is not a failure: it names a definition to look at, and the exit code stays 0. When a definition is over, look for rules that are duplicates, that are no longer needed, or that could be read only when they are needed, before cutting the meaning.
- A rule may also write `in_prompt: false`: it stays in the file and out of every member's prompt, with the day it was switched off in `off_since` when the screen wrote it. The rule keeps its id and its note, and `hergy validate` still counts it.
- To write, change or move a team's rules, read the `hergy-rules` skill first: it asks the person the questions one at a time, so they answer and never write YAML.
- Start in the project's `.hergy/`; ask the person before you change `~/.config/hergy/`.

## The web UI

- `hergy serve` serves the screens on 127.0.0.1, prints the URL and opens it in this machine's default browser; it holds the foreground until you stop it. Run it with `--no-open` when nothing should take the person's screen, and hand them the URL yourself instead.
- It answers this machine only. A write is a POST, PUT or DELETE from a page it rendered, carrying that page's token in the `X-Hergy-Token` header, so driving it with curl means reading the token out of a page first. Do not work around it.
- The screens read and write the same files the commands do. `hergy validate` still decides whether the settings hold.
- The band on every screen is four and all of them open: 活動, チーム定義, ロール and プロファイル. 活動 carries 活動 N and 待ち N beside it while this project has a team running: how many of its teams are running, and how many of them wait for a human or a permission (nothing is counted while herdr cannot be read, or none is running). The team definitions are at `/teams` (the list, with a toolbar above it that adds a definition — the new row opens at the top with プロジェクト / グローバル, a name to fill in and the files it would write listed — and each row carrying 複製, グローバルにコピー / プロジェクトにコピー and 削除; a row opens in place and is written where it stands: the トポロジー tab draws team.yaml as a figure — the human and the members as points, the turns as lines — and a turn is added or taken away by pressing a point or a line, with a card that shows what the change would do to the prompt before it is made, and a member's card carrying 複製, which adds the same member again (its role, profile, turns and worker purposes) under the next free name, and shows the team.yaml the row would write line by line beside the figure; and the ルール tab edits the team's own agreement.yaml with the same part the role screen uses; a tab at `/teams/yaml` keeps every team.yaml and agreement.yaml, the project's and the one outside it, as text). The activity screen is at `/activity` (this project's running teams — a row each with 許可待ち / 人間の番 / 止まっている / 仕事中, who the row is about and how long it has been that way; a row opens under itself into the newest question that row's own member asked, with its options, one line each for the older ones and `ほか N 件` for the rest, and 画面の最後, the last lines of that member's pane, with `▸ 上に N 行` for the lines held back; どうして止まっているか stands beside them: every member with when it stopped, newest first, and the workers under ワーカー; the screen reads itself again every ten seconds, and nothing on it is written — its three writes answer 405). The profiles are at `/profiles` (the list, with a row that opens and is written in place, the members' and workers' picks at `/profiles/assign`, and both profiles.yaml files as text at `/profiles/yaml`), and the roles at `/roles` (three tabs: 一覧, where a role's row opens in place and is written with its sections, rules, on/off switch, off day and note, beside a live preview of the Markdown a member's prompt will carry; 割り当て, where each team definition's members take a role; and YAML, where a role document stands as text with validate's problems beside it).
- The band carries a dot beside a screen that holds changes no save wrote, and walking to the other screen with the band carries those changes over and puts them back when that screen comes round again.
- The screens the old WebUI had are gone: `/definitions` and `/agreement`, and every path under them, answer 404 with the band on the page, as do `/team`, `/running`, `/rules`, `/diff`, `/bump`, `/figure` and `/panel`. A page that is still there moves instead: `/profiles/<name>`, and `/roles/<role>` with `/new` or `/<rule>` behind it, go to the list with that profile or role opened. What can be written today is a team definition (its team.yaml and its agreement.yaml), a role document and the two profiles.yaml files.
- Opening `hergy serve` lands on the activity screen while a team of a listed project is running (without `projects:`, a team of this project), and on the team definitions when none is.
- `hergy serve` is a headquarters for the projects you list: it shows the projects listed under `projects:` in the global `config.yaml` (absolute paths or `~/…`), each with its own teams, roles and profiles, and the running teams with their projects and workspaces. Without `projects:` it shows the project it was started in and the global settings. The sheet that Projects at the top of the screen opens lists and unlists projects; a team definition's 動き column starts and stops a listed project's team in a chosen herdr workspace, with the same result as `hergy up` and `hergy down`, and the band says 反映していない変更 N when a running team differs from its saved definition; the press opens the apply sheet, which reads `GET /api/apply`, shows each member's way of applying, what changed and whether the conversation goes, and applies the ticked members with `POST /api/apply`, the same as `hergy apply`. The sheet shows the progress and any question the agent asks while a member starts. The same reading answers under `/api/hq/` (`projects`, `teams`, `roles`, `profiles`, `running`, `workspaces`, `launch/options`, `launch`, `launches/<id>`, `apply`, `apply/count`, `stop`). A team is a tab labelled with its name that holds an agent or a pane named `<team>-<member>`, whether an agent runs there or not.
