# hergy

[English](README.md) | 日本語

コーディングエージェントを何体も並べて動かすこと自体は、もう難しくありません。[herdr](https://github.com/herdrdev/herdr) を使えば、ペインを割ってエージェントを起こし、エージェント同士で指示を送り合わせることまでできます。

難しいのはその先、並んだエージェントを**チームとして**働かせることです。進行を見る担当、要求を詰める担当、実装する担当と役割を分けると、仕事は確かに進むようになります。ところが、うまく回るほど決まりは書き足され、プロンプトは厚くなっていきます。毎回「エージェント同士でよしなに連携して」と頼み、その日のモデルの残量を見て担当を手で入れ替える。そしてある日、なぜうまくいっているのか自分でも説明できないことに気づきます。

hergy は、AI で楽してチームを組み、ものづくりをしたい人のための道具です。誰を、どの役割で、どのモデルで動かすかを YAML に書けば、そのチームを herdr の上に一度に立ち上げます。

## hergy は何をして、何をしないのか

hergy が持つのは、チームの編成と、決まりを重ねて見せる仕組みだけです。

それ以外は、もっと得意な道具に任せます。

- エージェントを動かすのは、Claude Code・Codex・OpenCode などの各エージェント CLI
- エージェントが動く場所と、エージェント同士の連絡は herdr
- 何が決まっていて何が未決なのかの記録は [gy](https://github.com/aq2bq/gy)

LLM もエージェント CLI も、月単位で姿を変えます。道具が責務を抱えるほど、その変化に置いていかれやすくなります。hergy が薄さにこだわるのはそのためです。

同じ理由で、hergy は決まりの中身も持ちません。役割ごとの振る舞いやチームの約束事は、使う人が自分の設定に書きます。hergy がするのは、それらを重ねてエージェントに渡すことと、どのファイルの決まりが効いているのかを見せることです。

チームが一番役に立つのは、手順の決まった流れ作業ではなく、やってみないと分からない仕事だと考えています。要求を詰める、記録と実態を照らし合わせる、人間の判断を引き出す、といった仕事です。決まった手順を自動で流したいなら、もっと向いた道具があります。

## いまの状態

作り始めたばかりです。チームの起動、役割の入れ直し、ワーカーの払い出し、設定の確認まではできますが、互換性はまだ約束できません。設定ファイルは書式の版（`version`）を持っていて、書式を変えるときは古い版を黙って読まずに止まります。版を移す `migrate` は、これから作ります。

最初にエージェントへ送るプロンプト（初期プロンプト）の既定の文は日本語で、まだ仮のものです。英語で使いたいときや、中身を自分で決めたいときは、`team.yaml` の `prompt` に自分のテンプレートを書いてください。

## インストール

```sh
go install github.com/aq2bq/hergy@latest
```

ほかに、[herdr](https://github.com/herdrdev/herdr) と、チームで使うエージェント CLI（`claude`、`codex`、`opencode` など）が必要です。

## はじめかた

設定は2種類のファイルと、役割ごとの Markdown でできています。まず、マシン全体で使うモデルの組み合わせ（プロファイル）を書きます。

```yaml
# ~/.config/hergy/profiles.yaml
version: 1
profiles:
  opus:  { kind: claude, args: ["--model", "claude-opus-5-5"] }
  codex: { kind: codex,  args: [] }
```

次に、チームを書きます。

```yaml
# ~/.config/hergy/teams/myteam/team.yaml
version: 1
docs: [protocol.md]      # 全員に渡す文書（任意）
members:
  - name: lead
    role: lead
    profile: opus
  - name: impl
    role: impl
    profile: codex
```

役割の中身は、チームのディレクトリの `roles/<役割>.md` に書きます。この例なら `roles/lead.md` と `roles/impl.md` です。全員に共通する約束事は `protocol.md` に書きます。

herdr のシェルペインの中で、まず起動せずに中身を確かめます。

```sh
hergy up myteam --dry
```

担当ごとに、どの役割ファイルとどの文書が使われるのか、展開済みのプロンプトが何なのかが出ます。よければ起動します。

```sh
hergy up myteam
```

新しいタブにペインが並び、各担当が起動して、それぞれに初期プロンプトが届きます。

## コマンド

| コマンド | すること |
|---|---|
| `hergy up [チーム]` | チームを起動する。`--dry` なら herdr に触れず、組み立てた計画を JSON で出す |
| `hergy refresh <担当>` / `--all` | 起動済みの担当に、初期プロンプトを送り直す。役割ファイルを直したあとや、エージェントの会話をリセットしたあとに使う |
| `hergy hire <名前> --profile P --purpose X --task "…"` | ワーカーを1人、別のタブに起動して仕事を頼む。ふつうは担当自身が使う |
| `hergy ls` | 見えるチームを、どの層にあるかと一緒に並べる |
| `hergy show <チーム>` | 層を重ねた最終形と、各値・各文書がどのファイルから来たかを出す |

どのコマンドも `--global` / `--local` で層を、`-C <ディレクトリ>` でプロジェクトの場所を指定できます。`refresh` と `hire` は `--team` でチームを指定します。

`refresh` は、担当が入力待ち（herdr の状態が `idle` か `done`）で、エージェントの種類が設定と一致しているときにだけ送ります。作業中の担当には送りません。

`hire` で起こしたワーカーは、終わったら頼んだ担当へ herdr 経由で報告します。誰がどの目的で、どのプロファイルのワーカーを起こしてよいかは `may_spawn` に書けます。ただし、これは担当のプロンプトに書かれるだけで、外れた払い出しも注意を出して通します。

## 設定の置き場と層

チームの設定は2か所に置けます。

| 層 | 置き場 |
|---|---|
| グローバル | `$XDG_CONFIG_HOME/hergy/`（未設定なら `~/.config/hergy/`） |
| ローカル | `<プロジェクト>/.hergy/` |

どちらも `teams/<チーム名>/team.yaml` を置きます。プロファイル（`profiles.yaml`）は、グローバルにだけ置きます。

チームは名前だけで呼びます。同じ名前のチームが両方にあれば、ローカルが勝ちます。名前を省くと、ローカルにチームが1つだけのときはそれを使い、それ以外は候補を示して止まります。プロジェクトの場所は git のルートで、git の外ならカレントディレクトリです。

設定が2か所に分かれると、どれが効いているのか分からなくなりがちです。そこで `hergy up` は、起動のたびに、担当ごとに読んだ役割ファイルと文書を、どちらの層のどのファイルかまで表示します。`hergy ls` は、ローカルがグローバルを上書きしているチームに印を付けます。

## team.yaml

```yaml
version: 1              # 必須
team: myteam            # 省略時はディレクトリ名
cwd: .                  # 担当の作業場所。プロジェクトの直下が基準
docs: [protocol.md]     # 全員に渡す文書。このファイルの場所が基準。ディレクトリなら中の *.md を名前順に
roles: [roles]          # 役割ファイルを探す場所。省略時は roles/
prompt: "…"             # 初期プロンプトのテンプレート（任意）
members:
  - name: lead          # herdr での名前。英小文字で始まる
    role: lead          # roles/lead.md を読む
    profile: opus       # profiles.yaml の名前。代わりに kind / args / env を直接書いてもよい
    cwd: .              # 任意。チームの値を上書き
    prompt: "…"         # 任意。チームの値を上書き
    may_spawn:          # 任意。払い出してよい目的とプロファイル
      purposes: [調査]
      profiles: [codex]
```

`docs` は書いた順に連結されます。書かなければ、文書は入りません。決まりを外して試したいときは、その文書を `docs` から外します。

役割ファイルは、`roles` に並べた場所を順に探し、最初に見つかった1つを丸ごと使います。見つからなければ、探した場所を示して止まります。

`args` と `env` の値は文字列だけを受け付けます。数値は引用符で囲んでください。

## profiles.yaml

```yaml
version: 1
profiles:
  opus:
    kind: claude                      # herdr のエージェントの種類
    args: ["--model", "claude-opus-5-5"]
  dev:
    kind: opencode
    args: []
    env:
      OPENCODE_CONFIG_CONTENT: '{"model":"…"}'
```

`args` は1要素ずつ、そのままエージェント CLI の引数になります。シェルは通しません。モデルや推論の強さの書き方は、エージェント CLI ごとに違います。インストールしてある CLI のヘルプに合わせてください。

`env` は、その担当のペインを作るときに環境変数として渡します。モデルを環境変数で受け取るエージェント向けです。

## 初期プロンプトの組み立て

テンプレートの中で、次の置換が使えます。

| 置換 | 中身 |
|---|---|
| `%{team}` / `%{role}` / `%{name}` | チーム名、役割、担当の名前 |
| `%{role_doc}` | 役割ファイルの中身（HTML コメントは除く） |
| `%{docs}` | `docs` の文書を順に連結したもの |
| `%{roster}` | チームの名簿 |
| `%{herdr}` | herdr での連絡の仕方 |
| `%{spawn}` | `may_spawn` がある担当にだけ、払い出しの許可と、そのまま打てるコマンド |

知らない置換を書くとエラーになります。テンプレートが読まなかった文書は、使ったことにはなりません。`hergy up` の表示にも出ません。

## これから

ここから先は、まだ計画です。

- **いま手番を持っているのは誰か**：herdr はエージェントが動いているか止まっているかを知り、gy は何が未決かを知っています。二つを重ねれば、チームのループが止まっていないかが見えるはずです（`hergy turn`）
- **担当どうしのやりとりを定型にする**：誰から誰へ、どの決まりに従って、どんな種類の連絡か。その記録が残れば、どの決まりが実際に使われているかを数えられます（`hergy pass`、`hergy log`）
- **決まりを部品として扱う**：決まりを一覧にし、なぜあるのかを引き、外して何回か動かして比べる（`hergy rules`）
- **人間の入口**：答え待ちの質問を1件ずつ受け取る、役割の名前で話しかける、気づいたことを一言残す（`hergy ask`、`hergy tell`、`hergy note`）
- **設定の手入れ**：作る、開く、ローカルで試してグローバルへ上げる、書式の版を移す（`hergy new`、`edit`、`fork`、`promote`、`migrate`）
- **チームの入れ子と TUI**

決まりは、少ないほど手入れが楽です。ただ、どこまで減らしてもチームが回るのかは、まだ分かっていません。それを測れるようにするのが、hergy の次の仕事です。
